Implement the missing corrected MVP workflow in the existing **Olyxee Logistics / Order Loop pnpm monorepo**, based on the completed verification report.

Do not introduce quote functionality. Staff and clients agree on pricing outside the platform. The system begins when staff create an order and invoice.

## Current verified baseline

Already working:

* Customer management
* Standard order creation
* Air and sea transport-mode workflows
* Backend status-transition validation
* Tracking events
* Email/SMS notification infrastructure
* Notification history and email retry
* Public customer tracking
* Tenant isolation
* Dashboard foundation

Missing or incorrect:

* No inline customer creation during order creation
* Orders have no agreed price, currency or additional charges
* No invoices
* Orders start at `ORDER_CONFIRMED` instead of `AWAITING_PAYMENT`
* No manual payment confirmation
* No backend payment gate
* No supplier tracking-number field
* No China warehouse receipts
* No unmatched-cargo queue
* No cargo-to-order matching
* Public tracking may expose internal status notes

Implement these gaps without rebuilding or replacing the working order, notification and tracking systems.

## Required workflow

```text
Staff selects or creates customer
→ Staff enters agreed price and shipment details
→ System creates linked order and invoice
→ System sends invoice to customer
→ Order remains AWAITING_PAYMENT
→ Staff confirms payment manually
→ Staff activates the order
→ Supplier sends cargo to China warehouse
→ Warehouse receives cargo and supplier tracking number
→ Staff links received cargo to existing order
→ Staff updates air/sea shipment statuses
→ Client receives notifications and views public tracking
```

## Phase 1: Order and invoice creation

### Extend the order model

Add appropriate order fields for:

* Agreed price/subtotal
* Additional charges
* Total amount
* Currency
* Transport mode
* Cargo type
* Service required
* Origin
* Destination
* Weight
* Dimensions
* Invoice association where appropriate

Use a safe money representation consistent with the current project. Prefer integer minor units if no established convention exists. Do not use floating-point values for financial calculations.

Preserve:

* Internal order ID
* Public tracking ID
* Order reference
* Existing customer association
* Existing shipment history
* Existing transport-mode status flow

### Add invoices

Create an `invoices` table linked to:

* Business/tenant
* Customer
* Order
* Creating staff member

Include:

* Internal invoice ID
* Unique tenant-scoped invoice number
* Subtotal
* Additional charges
* Total
* Currency
* Status
* Sent timestamp
* Paid timestamp
* Paid-confirmed-by staff member
* Created and updated timestamps
* Optional notes

Required invoice statuses:

* `DRAFT`
* `SENT`
* `PAID`
* `CANCELLED`

Only one active invoice should exist for an order in this MVP.

### Create order and invoice together

Update the order-creation operation so it:

1. Validates tenant ownership of the selected customer.
2. Accepts the agreed price and shipment information.
3. Creates the order.
4. Generates the invoice.
5. Links both records.
6. Creates the initial audit/tracking records.
7. Returns both the order and invoice.

Perform the database writes within one transaction.

The operation must be idempotent. Use an idempotency key or equivalent existing project convention so retries cannot create duplicate orders or invoices.

Do not roll back the successfully created order and invoice merely because the external invoice email fails. Record the failed delivery and allow staff to retry sending it.

### Inline customer creation

On the order-creation page:

* Allow staff to search and select an existing customer.
* Add a clear “Create new customer” option.
* Open an inline form or modal using the existing customer fields.
* Create the customer, select it automatically and continue the order flow.
* Prevent duplicate customer creation where the existing tenant-level uniqueness rules apply.

Do not require staff to leave the order page.

## Phase 2: Invoice delivery and manual payment

### Invoice interface

Add:

* Invoice detail page
* Invoice section on order details
* Invoice section on customer details
* Print/download using the browser’s print-to-PDF capability
* Send invoice action
* Retry failed invoice delivery
* Mark as paid action

The invoice sent to the customer must clearly show:

* Invoice number
* Business details
* Customer details
* Order reference
* Shipment/service description
* Subtotal
* Additional charges
* Total
* Currency
* Payment instructions if configured
* Due date if provided

Reuse the existing email and notification infrastructure where practical. Record delivery state and errors.

No payment gateway must be added. The existing Paystack subscription billing is unrelated and must not be reused for customer invoice payments.

### Payment confirmation

Add a tenant-protected backend operation for staff to mark an invoice as paid.

It must:

* Confirm the invoice and linked order belong to the authenticated business.
* Record `paidAt`.
* Record the staff user who confirmed payment.
* Be idempotent when repeated.
* Create an audit event.
* Make the linked order eligible for activation.

Do not allow the frontend to set arbitrary payment timestamps or staff identifiers.

## Phase 3: Payment-gated order activation

Add `AWAITING_PAYMENT` as the initial state for logistics orders.

Required behaviour:

* Every new logistics order starts at `AWAITING_PAYMENT`.
* Shipment status transitions are blocked while its invoice is unpaid.
* Staff can activate the order only after its invoice is `PAID`.
* Activation moves the order from `AWAITING_PAYMENT` to the appropriate first active logistics state, such as `ORDER_CONFIRMED`.
* Payment and activation are separate auditable actions.
* Repeated activation requests must not create duplicate events.
* Backend enforcement is mandatory; hiding UI buttons is insufficient.

Update all shared status definitions and consumers consistently:

* API validation
* Order-status library
* Admin status picker
* Order timeline
* Public tracking timeline
* Notification copy
* Tests
* Generated schemas where applicable

Preserve backward compatibility for existing orders already in active shipment states. Do not force historical orders back into `AWAITING_PAYMENT`.

## Phase 4: China warehouse receipts and cargo matching

### Extend orders

Add nullable fields:

* `supplierTrackingNumber`
* `supplierTrackingNumberAddedAt`
* `supplierTrackingNumberAddedBy`
* `chinaWarehouseReceivedAt`

The supplier tracking number is unknown during order creation and must remain optional until the cargo arrives.

Keep it separate from:

* Internal database ID
* Public tracking ID
* Order reference
* Invoice number

Never use it as a primary key or public tracking credential.

Add a tenant-scoped duplicate constraint or safe equivalent preventing the same normalized supplier tracking number from being assigned to multiple active orders within one business.

Normalize surrounding whitespace and casing appropriately without corrupting valid tracking-number characters.

### Warehouse receipts

Create a `warehouse_receipts` table containing:

* Receipt ID
* Owning business
* Supplier tracking number
* Linked order, nullable
* Receipt status: `UNMATCHED` or `MATCHED`
* China warehouse received timestamp
* Package count, optional
* Weight, optional
* Notes, internal only
* Cargo-photo URL metadata, optional
* Created by
* Matched by and matched timestamp
* Created and updated timestamps

Binary upload/storage is outside this task. Store photo URL metadata only if the existing application supports safe URLs.

### Warehouse interface

Add:

* `/warehouse-receipts`
* `/unmatched-cargo`

Staff must be able to:

1. Record cargo received at the China warehouse.
2. Enter its supplier/courier tracking number.
3. Search existing orders using:

   * Order reference
   * Customer name
   * Company name
   * Phone
   * Email
4. Select and link the correct existing order.
5. Save cargo as unmatched when the order cannot be identified.
6. Open unmatched cargo later and link it.
7. See warnings when a tracking number is already assigned.
8. View the receipt from the linked order page.

Matching must:

* Be transactional.
* Enforce tenant isolation.
* Reject cross-business matches.
* Add the supplier tracking number to the order.
* Record the China warehouse received timestamp.
* Mark the receipt as matched.
* Record matching staff and timestamp.
* Create audit and tracking events.
* Move the order to `RECEIVED_FROM_SUPPLIER` only when that transition is valid.
* Trigger the existing customer-notification process where appropriate.
* Remain safe under repeated requests.

An unpaid or inactive order must not silently enter the shipping workflow through warehouse matching. If cargo arrives before payment confirmation, allow staff to record and link the receipt, but keep the order payment-blocked and clearly flag the situation for staff.
